# LIM-107 — Hermes V2 Provider: Research & Design

Status: design artifact only. No source, registry, service, profile, session, or Linear changes accompany this document. Scope follows the accepted story contract: an **additive** Hermes V2 adapter under the LIM-75 provider plane; V1 unchanged; disposable profile/session only; **no real seat hookup**. Console acceptance is not claimed here.

Evidence bases:

- Console: `/srv/work/lhc-console` @ `3f28178` (branch `main`), primarily `docs/LIM-75-console-v2-interactive-provider-plane.md` and `apps/server/src/v2/*`.
- Hermes: `/srv/work/hermes-agent` @ `166709c63` — the **Hermes-LHC** fork (`hermes_lhc_product.py:13-17`: `PRODUCT_NAME = "Hermes-LHC"`, `REQUIRED_CONTEXT_ENGINE = "lhc"`), Python package `hermes-agent` 0.20.2, upstream tag `v2026.8.16`, LHC source tag `lhc-source-2026.08.17`.

Normative labels follow LIM-75: **SETTLED** (this design commits), **OPEN** (decided here but revisitable), **OBLIGATION** (claim that must be proved during implementation/live acceptance, not asserted now), **UNSUPPORTED** (explicitly out).

## 1. Resolution of the prior research question: gateway vs in-process worker

**SETTLED: a separate supervised persistent Hermes worker process per Console V2 target — not attachment to a live `hermes serve`/`hermes dashboard` gateway, and not an in-process Python embedding.**

Source evidence:

1. Hermes' own shipping Ink TUI does exactly this. `ui-tui/src/gatewayClient.ts:343-357` spawns `python -m tui_gateway.entry` with piped stdio and drives it as newline-delimited JSON-RPC 2.0. A per-client supervised child is the reference topology, not a workaround.
2. The WebSocket gateway path is the _same_ dispatcher, not a richer one. `tui_gateway/ws.py:12-19`: the WS handler "Reuses `tui_gateway.server.dispatch` verbatim… No framing differences." Attaching to a live gateway buys nothing protocol-wise and costs: ticket auth (`?ticket=` single-use 30 s TTL, `hermes_cli/web_server.py:15500-15560`), cross-session GIL contention in one Python process, and — decisively — **mutating a live gateway**, which the story contract forbids and which Hermes' own release notes gate behind "separate explicit authority" (`docs/releases/lhc-source-2026.08.17.md`).
3. Process-global MCP registration argues for one process per profile: "in a multi-profile process the FIRST profile that builds an agent wins the discovery slot" (`tui_gateway/entry.py:281-300`, upstream #67605). A dedicated worker with one profile sidesteps this class of bug entirely.
4. Console-side, LIM-75 Q2 already settles the supervision model: runtimes are **console children** in a killable process group inheriting the writer-lock fd (`policies.ts:19`; `manager.ts:609-616` rejects `detached`). A stdio child worker slots into this unchanged; a remote WS gateway would require the deferred `detached` policy (LIM-75 D5).

In-process embedding (`run_agent.AIAgent`) is rejected because Console is a Node process; there is no Python-in-process option, and shelling into `hermes -z` one-shots is the V1 plane, not V2 interactive.

Contradicting evidence considered: `hermes serve` exists precisely to multiplex remote clients, and the compute-host child (`tui_gateway/host_supervisor.py`) shows Hermes itself isolates turns into children when serving many sessions. Neither contradicts the worker choice — they confirm that per-child isolation is idiomatic and that the gateway adds multiplexing Console does not need (Console already owns one runtime per target).

## 2. Runtime boundary and transport

**SETTLED.**

- Worker command: `python -m tui_gateway.entry` (module invocation, matching `gatewayClient.ts`), spawned by the V2 `RuntimeManager` through the existing `spawnFencedChild` path so the abstract-socket writer fence fd 3 is inherited (`writer-lock.ts:38`).
- Environment (explicit, never inherited-by-default; merged under the existing `scrubbedEnv` precedent from `docs/handoff-env-scrub.md`):
  - `HERMES_HOME=<disposable profile home>` — always explicit; `hermes_constants.py:80-104` warns that an unset `HERMES_HOME` plus a sticky `active_profile` file silently rebinds the home. The adapter must never rely on the default home.
  - `PYTHONPATH` / `HERMES_PYTHON_SRC_ROOT` pointing at the Hermes checkout, `PYTHONUNBUFFERED=1` (`tui_gateway/transport.py:49-59` warns Python stdout is block-buffered on a pipe).
  - No `HERMES_YOLO_MODE` and no approval bypass in the default posture; approval policy is §7.
- Wire: newline-delimited JSON-RPC 2.0 over stdio, one object per line, no `Content-Length` framing (`tui_gateway/ws.py:12-19`). Reuses Console's existing `StreamJsonlTransport` (`apps/server/src/v2/jsonl-transport.ts`) — same shape as the Codex app-server transport.
- Readiness: the worker emits `{"method":"event","params":{"type":"gateway.ready",...}}` as its first frame (`tui_gateway/entry.py:355-366`). The adapter treats `gateway.ready` as the initialize handshake; a bounded wait (reusing the Codex `RPC_TIMEOUT_MS = 30_000` pattern) applies, since agent build is deferred to first prompt and can take up to `agent.build_wait_timeout` (600 s default, `server.py:2170-2255`) — see §4 for how turn-start timeouts differ from RPC timeouts.
- Errors: JSON-RPC error envelope with app codes (`4002` text required, `4006/4007` session id, `4009` busy/subagent, `4010` unsupported, `4090` session cap, `5xxx` internal — `tui_gateway/server.py`). The adapter maps transport/spawn failures to `ProviderUnavailableError` and `4010`-class responses to `ProviderUnsupportedError`, preserving error classes per the `c35c5eb` norm (classification by `instanceof`, never message sniffing).
- Child lifecycle norms carried over verbatim from the Codex/Pi adapters: `"error"` subscribed immediately at spawn (`d238c71`), stderr drained into a bounded 8 KiB tail used as start evidence never verdict, per-child evidence reset, bounded stop with SIGKILL escalation via `stop-escalation.ts` (`d4e35a6`), no `exited` without an observed exit and `StopUnprovenError` otherwise (`3aea5a7`).
- Graceful stop: close stdin + SIGTERM. The worker honors SIGTERM with `HERMES_TUI_GATEWAY_SHUTDOWN_GRACE_S` (default 1.0 s) then `os._exit(0)` (`entry.py:88-176`); Console's `GRACEFUL_STOP_TIMEOUT_MS = 5_000` window comfortably contains it, then `killHard` (process group, then child), then `KILL_SETTLE_TIMEOUT_MS`.

**UNSUPPORTED in this design:** WS attachment to `hermes serve`, the compute-host `turn_isolation` topology, unix sockets (none exist in Hermes), and any modification of a running gateway or shared profile.

## 3. Disposable profile and session

**SETTLED.**

- The adapter operates only on a **disposable Hermes profile home** provisioned for the target (e.g. `~/.hermes/profiles/lhc-v2-<target>/` or a fully separate `HERMES_HOME` under a scratch root). A profile home is a complete `HERMES_HOME` (own `config.yaml`, `state.db`, `lhc/threads/`) per `hermes_cli/profiles.py:270-282`. Provisioning is out of adapter scope (operator/fixture concern); the adapter receives the home path via registry config and refuses to start without it.
- Hermes-side session identity: durable `session_key` = `YYYYmmdd_HHMMSS_<6hex>` minted by the gateway (`server.py:7070-7071`); the live RPC `sid` is an 8-hex ephemeral handle (`methods_session.py:16`). `session.create` deliberately writes **no** DB row; rows materialize on first turn (`methods_session.py:114`). The adapter therefore treats _first turn_, not create, as the point where canonical state can exist.
- Sequence on `start()`: wait `gateway.ready` → `session.resume {session_id: <configured session>, lazy?...}` (or `session.create` for a fresh disposable session in the deterministic lane) → canonical identity proof (§6) → emit `threadAttached`. Resume follows the compression-continuation chain to the live tip via `db.resolve_resume_session_id` (`methods_session.py:374-381`), so a rotated parent id still binds — the adapter must record the _resolved_ session id as `nativeThreadRef`.
- No real seat hookup: the design never points the adapter at a user's default `~/.hermes` home or an operator's live profile. Live acceptance (§12) runs against a purpose-made disposable home only.

## 4. Ordinary turn and event streaming

**SETTLED**, mapped onto the LIM-75 canonical event kinds (`turn.started`, `turn.item`, `turn.completed`; envelope and `seq` are Console-assigned — adapters never assign `seq`, LIM-75 §8).

Submit: `prompt.submit {session_id, text}` (`tui_gateway/methods_prompt.py:268-…`), returning `{"status":"streaming"}` (or `queued`/`steered`/`redirected`, which the adapter treats per §5). Text is sanitized server-side. The submit rebinds the session's transport to the caller (`methods_prompt.py:340-341`), which is what grants steering authority (§5).

**Native turn id.** Hermes events carry `session_id` but no turn id; the session's `running` flag is the turn mutex and exactly one turn is active per session. Following the Pi precedent (`pi-lhc.ts:592` `correlatePiNativeTurnId`), the adapter **mints** a correlated native turn id `hermes-rpc:<runtimeGeneration>:<jsonrpcRequestId>` from the `prompt.submit` request id, and never invents a synthetic id when the request id is unavailable (refuse instead). Correlation of subsequent events to this turn id is by the single-active-turn invariant, scoped to (session, generation): events received between the accepted `prompt.submit` response and the terminal `message.complete` belong to that turn.

Event normalization (`ProviderNotification` in `adapter.ts:56-91`; item types `agent_message | tool | other`):

| Hermes event (`tui_gateway/server.py`)                                        | Adapter notification                                                                                                                                                                                                                                                                             |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `message.start`                                                               | `turnStarted {nativeTurnId}`                                                                                                                                                                                                                                                                     |
| `message.delta {text}`                                                        | accumulated into final text; optionally surfaced as streaming `item` if/when the plane grows delta items — initially buffered, **not** emitted per-token (matches Codex adapter granularity)                                                                                                     |
| `reasoning.delta` / `thinking.delta` / `reasoning.available`                  | `item {type:"other", kind:"reasoning"}` — one item per `reasoning.available` block (`server.py:5849-5852`); per-token deltas are not forwarded                                                                                                                                                   |
| `tool.start {tool_id, name, context}` (`:5752-5770`)                          | `item {type:"tool", phase:"start"}`                                                                                                                                                                                                                                                              |
| `tool.complete {tool_id, name, args, result, summary?}` (`:5774-5817`)        | `item {type:"tool", phase:"complete"}` — note Hermes suppresses `tool.complete` unless tool-progress is enabled or the tool is lifecycle-required; the adapter enables tool progress at session setup (`HERMES_TUI_TOOL_PROGRESS` / `tools.configure`) — OBLIGATION O5 verifies the exact switch |
| `status.update {kind, text}` (`:1978-1991`)                                   | `item {type:"other", kind:"status"}`; `kind:"compacting"` additionally recorded as runtime evidence                                                                                                                                                                                              |
| `message.complete {text, usage, status}` (`:10929-10967`)                     | `turnCompleted {outcome, finalText}` with `complete→ok`, `interrupted→interrupted`, `error→error(+recoverable flag)`; `error`-status turns are retained by Hermes as inflight (`server.py:8211-8219`) and recoverable via resume                                                                 |
| `session.info`, `session.usage`, `notification.show`, all `*.request` prompts | `item {type:"other"}` or start-evidence recording; never fatal (config-warning precedent from `c35c5eb`)                                                                                                                                                                                         |

Final event: `message.complete` is the sole terminal frame per turn; the adapter emits exactly one `turnCompleted` per minted turn id. WS-side token coalescing (`ws.py:44-58`) does not apply on stdio; ordering on stdio is line order and the adapter relies on it.

## 5. Redirect / steer semantics

Hermes has genuinely distinct steer and redirect verbs (unlike Codex's single `turn/steer`), so the mapping is explicit:

- **Console `steer` command → `session.steer`** (`methods_session.py:3379-3413`). Hermes semantics (`run_agent.py:3404-3438`): text is appended to the last tool result of the current batch; no interrupt, no new user turn; multiple steers concatenate; never escalates to hard interrupt (#86134). Return `{"status":"queued"}` maps to `AdapterSteerResult "ok"` → receipt `applied {effectStage:"queued"}`; `{"status":"rejected"}` maps to `"mismatch"`. Adapter-side fence: the steer is refused unless the supplied `nativeTurnId` equals the adapter's current minted turn id (same fence as `pi-lhc.ts:176-186`).
- **Console redirect (if/when the plane exposes it) → `session.redirect`** (`methods_session.py:3416-…`; `run_agent.py:3440-3500`): cancels only the in-flight model request, keeps completed tool results, appends the correction as a real user message, retries; degrades to steer during tool execution. **OPEN:** the current `ProviderAdapter` interface has no `redirect` method — slice 1 ships steer-only and records redirect as a capability-matrix "N (provider) / – (plane)" row rather than widening the shared interface unilaterally. Widening the interface is a paired-provider decision per LIM-75 §9.3 (no row ships for one provider alone).
- **Steer consumption: UNSUPPORTED**, declared in `PROVIDER_CAPABILITIES` as `steerConsumption:"unsupported"`, same as Codex and Pi (`adapter.ts:19-35`). Evidence: the steer text is spliced into a tool result with no correlating id on any subsequent event; positional inference is exactly what the plane forbids ("only `command.effect{stage:"consumed"}` proves consumption", LIM-75 §6.5, and the Codex adapter's deliberate `userMessage` drop, `codex-lhc.ts:363-368`).
- **Steering authority caveat (Hermes-specific):** authority is transport-bound, not id-bound — `_current_session_steer_authority` (`server.py:2070-2092`) requires the requesting transport to _be_ the session's bound transport, which rebinds on `prompt.submit`/resume. Because the adapter owns the worker's only stdio transport and issues the submits, it holds authority by construction; this invariant is stated so reconnect logic (§9) preserves it (a fresh worker must resume before steering).

## 6. Canonical LHC identity

**SETTLED**, following the `c35c5eb`/`3aea5a7` norms exactly: identity is proved from the canonical store's own resume reference, never by string equality.

- Hermes is Console's registry-less **scan host**: canonical threads live at `<HERMES_HOME>/lhc/threads/<stem>.sqlite` (default and per-profile roots, `packages/core/src/hosts.ts:85-108`), and the resume recipe is `hermes [--profile p] --resume <sessionId>` with `sessionRef = thread.sessionId` — the thread **file stem** (`packages/core/src/launch.ts:187-195`, `:21` "hermes session stem").
- Proof: the adapter's `start()` requires `proveCanonicalSession(nativeThreadRef, canonicalThreadId)` (refusing to start without it, per `codex-lhc.ts:168-174`), where the manager's prover reads the disposable profile's canonical store through the read-only `@lhc-console/core` path (`canonical.ts:15-104`) and accepts only `span.nativeThreadRef === resolvedHermesSessionId` derived from `launchRecipe(thread)?.sessionRef`. Missing spans, inspector errors, and field-less summaries reject even when strings match.
- **OBLIGATION O1:** that the Hermes-LHC fork writes the gateway `session_key` as the LHC thread stem (i.e. `sessionRef === session_key`). The fork mandates LHC (`hermes_lhc_product.py:86-136`) and Console's scan host models the layout, but the stem↔session_key equality was not proved from source in this pass. Slice 2's deterministic test constructs a real hermes-layout store and wires the real prover (the `v2-codex-startup-repair.test.ts` pattern: real producer → real consumer); live acceptance confirms against a real disposable profile. Until O1 passes, no identity claim is made.
- Hermes sessions have no cwd-based newborn association (`matchCwd: null`, `newsession.ts:132-148`) — identity flows only through the profile home + session stem. The writer resource key is the existing `sha256(hostHome \0 canonicalThreadId)` (`identity.ts:52-54`) with `hostHome` = the disposable profile home.
- The Console never writes canonical content: LIM-75 §7.4 applies unchanged. Hermes' own `state.db` is Hermes-internal and the adapter never opens it.

## 7. Status, approvals, and capability posture

- Runtime status flows through the existing manager states (`starting/idle/turn.active/unknown/stopped`); the adapter contributes `getState()` from its transport + last terminal frame, and `session.status`/`session.usage` payloads are recorded as evidence items, not status authority.
- **Approvals: UNSUPPORTED in slice scope** (mirrors Codex Q4: `codex-lhc.ts:127-178` rejects `surface-server-requests`). The disposable profile is configured so no approval can block a turn in the deterministic lane; `approval.request` events, if they occur, surface as `other` items and the turn outcome remains truthful (a turn wedged on approval eventually resolves via interrupt/stop, never a fabricated completion). No auto-approve and **no YOLO mode** in the default posture; whether live acceptance uses a constrained toolset (`HERMES_TUI_TOOLSETS`) or `approvals.mode: off` scoped to the disposable profile config is OBLIGATION O6 (choose the least-privilege option that keeps the lane deterministic; never touch global config — per-session overrides are explicitly never written globally, `methods_session.py:46-72`).
- Images, PDFs, slash commands, subagents, voice, model switching: all exist on the wire (`image.attach`, `commands.catalog`, `subagent.*`, `model.options`) but are **UNSUPPORTED** by this adapter — declared `–` in the matrix, never emulated.

## 8. One writer

**SETTLED**, reusing the plane's fence unchanged:

- Exclusion primitive: Console's abstract-namespace unix-socket fence keyed by the canonical writer resource (`writer-lock.ts:1-26`), acquired before the worker spawn and inherited as fd 3. Ownership metadata stays inspectable-only.
- Hermes's `writerPolicy` in core is `shared` with an explicit "Not formally confirmed" caveat (`hosts.ts:29-33`). LIM-75 §7.2 already settles this: V2 treats every provider as single-writer for its own runtime. This design follows that; no `hosts.ts` change is proposed.
- Hermes's own `active_sessions.json` lease (`hermes_cli/active_sessions.py:279-344`) is a **concurrency cap, not a writer lock** — it does not prevent two processes attaching to one session id, and two agents on one `session_key` interleave the transcript (Hermes's own guard comment, `methods_prompt.py:367-374`). It is therefore evidence, never the exclusion primitive. The one-writer incident memory (never attach two processes to one session id) is enforced structurally: one fenced console-child worker per target, fence keyed on the profile-home+stem resource.

## 9. Command/event correlation, receipts, duplicates/gaps, restart/reconnect

All plane-level machinery is reused verbatim (store, seq assignment, SSE replay, `410` re-baseline, idempotent `commandId`, expected-turn fencing at acceptance and application — LIM-75 §§6.5–6.6, §8). Hermes-specific bindings:

- **Receipts.** `start` → `applied` only after `session.resume` success **and** canonical proof **and** `threadAttached`. `send` → `applied {nativeTurnId}` on the accepted `prompt.submit` response (JSON-RPC result observed); the request id is the durable correlation token recorded with `dispatch_state`. `steer` → §5. `interrupt` → `applied` on `session.interrupt` result; terminal truth is the subsequent `message.complete {status:"interrupted"}`. A `prompt.submit` written as `sending` whose response was never observed (worker died mid-line) settles `indeterminate`, upgradeable to `applied` only if a later resume's `inflight` snapshot uniquely correlates (see below) — never by timing.
- **Duplicates.** Hermes emits no event sequence numbers; the stdio line order is the only provider ordering and Console's transactional `seq` assignment is the durable order. `commandId` idempotency prevents double-submit; the adapter never retries `prompt.submit` on its own (a retry would start a _second_ turn, not deduplicate — Hermes queues rather than rejects concurrent submits, `server.py:7971-8062`, which makes blind retry actively dangerous; this asymmetry vs providers that reject is called out in the matrix).
- **Gaps / reconnect.** stdio has no reconnect: worker death is terminal for that generation. Recovery is **restart, not reattach**: new generation → new worker → `session.resume` → Hermes returns the retained `inflight` payload for a turn that missed its terminal frame (`server.py:8180-8219`), which the adapter surfaces as evidence to settle the prior generation's `indeterminate` send/steer receipts where the payload uniquely correlates (user text match is _not_ unique correlation; only resolve when Hermes's inflight `user`/`corrections` structure can be tied to the recorded dispatch — **OBLIGATION O2** to determine from source whether a unique token exists; if not, those receipts stay `indeterminate`, honestly). Manager-side boot reconciliation (LIM-75 §8.4: `unknown` until owner/lock/PID reconciled, fence held on unproven outcomes, no auto-restart) applies unchanged.
- **Session TTL caveat:** the worker reaps idle sessions after `_SESSION_TTL_S` (6 h default, `server.py:1218`). The adapter pins the session by treating a `session.info`/reclaim signal as `exited`-equivalent evidence and sets `HERMES_TUI_SESSION_TTL_S` generously for the worker it owns — OBLIGATION O3 confirms reclaim emits an observable frame on stdio.

## 10. Stop, cleanup, rollback

- **Stop:** §2 sequence (stdin EOF + SIGTERM → 5 s → SIGKILL group/child → 2 s settle → `StopUnprovenError` if no observed exit; fence retained, runtime `unknown`). `session.interrupt` precedes graceful stop in `interrupt`/`drain` modes so Hermes denies pending approvals and clears queues itself (`methods_session.py:3102-3172`); background processes Hermes spawned are not reaped by interrupt (documented Hermes behavior) — the process-group SIGKILL in `killHard` is the backstop, and the worker runs in its own killable group per Q2.
- **Cleanup:** on proven exit — unsubscribe, release fence, delete live entry (existing manager path). Disposable-profile deletion is an operator action outside the adapter; the adapter never deletes a profile home.
- **Rollback:** fully additive. The Hermes adapter is a new file plus enumeration-point registrations (`V2_PROVIDERS`, `PROVIDER_CAPABILITIES`, `AdapterFactory` wiring in `apps/server/src/index.ts`, agent-registry `v2.provider` validation — the five points inventoried from `3f28178`). Rollback = remove the `v2` block from any hermes agent entry and/or revert the additive commits; V1 relay, the scan-host Finder path, and both existing V2 providers are untouched. The plane's `LHC_CONSOLE_V2=1` flag continues to gate everything.

## 12. Implementation slices and acceptance

Lean, additive, in the established order (each slice lands with its tests; nothing ships on assertion):

- **Slice 1 — adapter + deterministic wire lane.** `apps/server/src/v2/adapters/hermes-lhc.ts` implementing `ProviderAdapter`; enumeration-point registrations; `PROVIDER_CAPABILITIES.hermes` per §11. Tests in the `v2-adapters.test.ts` pattern: an in-memory JSONL Hermes fixture (`MemoryJsonlPair`) scripting `gateway.ready`, `session.resume`, `prompt.submit`, the event stream of §4, steer queued/rejected, interrupt, error-status terminal, malformed line, `4009` busy, and child-failure containment (nonexistent python, mid-turn death) — mirroring the Codex/Pi fixture suites and the stop-truth lane (`v2-stop-escalation.test.ts` patterns reused as-is since `stop-escalation.ts` is shared).
- **Slice 2 — canonical identity, real producer → real consumer.** A `v2-hermes-startup-repair`-style test constructing a real hermes-layout canonical store (per-profile `lhc/threads/<stem>.sqlite`) on a tempdir, wiring the real `inspectCanonicalSpan` through the real manager prover into the real adapter over the memory transport; positive stem match, foreign stem rejection, field-less span rejection. Discharges O1's deterministic half.
- **Slice 3 — manager/contract integration.** Paired contract coverage in the `v2-contract.test.ts` harness (real `V2Store`, real `RuntimeManager`, Fastify inject) with `FakeProviderAdapter` extended only if a Hermes-shaped behavior (queue-on-busy submit) needs modeling; receipts, fencing, writer-conflict, restart reconciliation paths exercised for the hermes provider id.
- **Slice 4 — live acceptance (env-gated, disposable only).** A `LIVE`-gated lane, absent today for all providers, run manually against a purpose-created disposable `HERMES_HOME`: worker spawn → ready → create+first turn (materializes the session row and canonical thread) → restart-and-resume with identity proof (discharges O1 live) → steer queued receipt → interrupt → stop with proven exit → tool-progress switch check (O5) → TTL/reclaim observability (O3) → inflight-correlation determination (O2) → approval posture (O6). Results recorded as evidence in the doc's successor, LIM-75 §13.2-style: named checkout, per-file citation, unproven items listed as obligations — never asserted.

**Obligations register:** O1 stem↔session_key identity; O2 inflight unique-correlation token; O3 TTL reclaim observability; O4 (folded into slice 1) exact `session.create` vs `session.resume` parameter set for a disposable session including `profile` interplay when `HERMES_HOME` is already the profile home (prefer explicit `HERMES_HOME`, no `profile` param — verify no double-binding); O5 tool-progress enablement switch; O6 least-privilege approval posture for the live lane.

## 13. Out of scope / explicitly unsupported

Real seat hookup; production handoff (unsupported plane-wide, LIM-75 status header); detached/daemonized runtimes (D5); WS gateway attachment; approvals surfacing (Q4); steer-consumption proof; redirect at the plane interface; multi-session multiplexing in one worker; any Hermes-side code, config, profile, or gateway change; Linear updates; Console acceptance claims.
